# Codex Atlas 方案设计

## 目标

Codex Atlas 是一个 Windows 个人自用的轻量桌面侧边栏工具箱，用来扫描、展示和整理本机 Codex 的 `skills`、`plugins`、`tools` 和 `apps`。它不是聊天工具，也不修改 Codex 自身配置；它只读 Codex 数据，把能力整理成一个可搜索、可收藏、可复制调用模板的能力字典。

## 约束

- 只允许本项目目录内增删改文件。构建缓存、依赖缓存、测试产物和打包产物都必须放在项目内。
- 可以只读访问 `C:\Users\Administrator\.codex` 等 Codex 数据目录，但不能写入、删除或移动其中任何文件。
- 扫描、统计、AI 整理都由用户手动触发，不做默认后台持续扫描。
- 个人数据优先级最高：备注、收藏、隐藏、手动标签、自定义模板不能被 AI 整理覆盖。
- 代码要有必要中文注释，重点覆盖扫描、索引、合并、统计、外部命令和边界处理。
- UI 以浅色调为主，启动后第一屏就是可用的能力字典界面。

## 技术选型

### 方案 A：Go + Windows 原生控件库 `github.com/lxn/walk`

- 优点：本机已安装 Go；可产出单个 Windows 可执行文件；不需要 Electron/WebView；常驻内存和启动速度通常优于 Node 桌面壳；可以直接调用 Win32 能力实现置顶、快捷键、打开文件和剪贴板。
- 风险：UI 表达力不如 Web 前端；需要围绕 Windows 平台开发；需要把 Go 模块缓存固定到项目内，避免污染外部目录。
- 适配度：高。项目明确只做 Windows 自用侧边栏，原生控件和单文件交付比跨平台能力更重要。

### 方案 B：Node + Electron

- 优点：UI 开发快，视觉表现强，生态成熟。
- 风险：体积大、内存占用高、启动慢，不符合“轻量、快、低 CPU/内存”的第一优先级。
- 适配度：低。除非后续要大量复杂前端交互，否则投入产出比不合适。

### 方案 C：Python + Tkinter/PyInstaller

- 优点：实现快，标准库自带 Tkinter，学习和调试成本低。
- 风险：打包体积和启动速度不稳定；Tkinter 视觉较朴素；PyInstaller 产物和杀软误报风险更高。
- 适配度：中低。适合原型，不适合作为最终轻量桌面小工具。

### 结论

选择 **Go + `github.com/lxn/walk`**。理由是它最贴近本项目的核心约束：Windows 单机、自用、快速启动、低常驻占用、便携交付、不引入浏览器壳。所有 Go 命令执行时设置：

```powershell
$env:GOMODCACHE = "$PWD\.cache\gomod"
$env:GOCACHE = "$PWD\.cache\gobuild"
$env:GOPATH = "$PWD\.cache\gopath"
```

这样依赖、编译缓存和中间文件都停留在当前项目内。

## 产品形态

主窗口是一个浅色短侧边栏，默认靠屏幕右侧显示，宽度约 460px，高度约 640px；用户可以手动拖高，拖高后列表区域优先扩展。窗口支持置顶和全局快捷键显示/隐藏。第一屏包含：

- 顶部品牌区、搜索框和视图切换：`Skills`、`Plugins`、`Tools`、`Apps`。
- 快速过滤：常用、调试、写文档、设计、隐藏。
- 原生轻量主列表：能力名称、手动/AI 标签、真实使用次数。
- 底部详情抽屉：摘要、来源路径、类型、调用模板和高频动作。
- `更多` 面板：文件/路径、完整详情、刷新、排序、AI 整理等低频动作。
- `编辑` 面板：别名、标签、自定义模板、备注、收藏、隐藏和保存整理。

为保持轻量，MVP 使用 Windows 原生控件完成清晰可用的界面，不引入 Electron/WebView，也不追求复杂动画。主列表优先使用原生绘制，避免自绘回调在不同系统主题下失效。

刷新、统计、AI 整理等后台动作由 UI 层串行化，任务运行期间禁用相关按钮，避免重复触发后台任务或与个人整理保存并发写入。使用统计会缓存到项目内 `data/stats-cache.json`，启动时直接读取新版缓存，避免每次打开都全量扫描历史会话；旧版缓存会显示为未知统计。AI 整理接收的是当前可见列表，确保搜索、快速筛选和隐藏筛选的语义一致。

## 数据模型

数据分三层合并：

1. 原始数据：从 Codex 本地文件和运行时可见结构只读扫描得到。
2. AI 数据：中文摘要、AI 标签、调用模板、适用场景、不适用场景、相似能力。
3. 用户数据：别名、手动标签、备注、收藏、隐藏、自定义模板、个人排序。

合并规则：

- 原始数据每次扫描可重建。
- AI 整理只更新 AI 数据。
- 用户数据只由用户操作更新，永远不被扫描和 AI 覆盖。
- 展示时优先使用用户别名和用户模板；标签为用户标签 + AI 标签去重合并。

项目内持久化文件：

- `data/atlas-store.json`：用户数据、AI 数据和轻量设置。
- `data/last-scan.json`：最近一次扫描结果缓存，用于快速启动展示。

## 扫描设计

扫描器只读以下位置：

- `CODEX_HOME` 环境变量指定目录。
- 未设置时使用 `%USERPROFILE%\.codex`。
- `skills/**/SKILL.md`。
- `plugins/cache/**/.codex-plugin/plugin.json`。
- 插件声明的 `skills` 目录和常见 `skills/**/SKILL.md`。
- `sessions/**/*.jsonl` 用于统计 skill 出现和使用情况。

Skill 解析规则：

- 优先读取 `SKILL.md` 的 YAML front matter：`name`、`description`。
- 没有 front matter 时，使用目录名作为真实名称，首个 Markdown 标题或首段文本作为说明。
- 插件 skill 使用 `pluginName:skillName` 作为展示真实名称，避免和本地 skill 重名。

Plugin 解析规则：

- 读取 `.codex-plugin/plugin.json` 的 `name`、`version`、`description`、`interface.displayName`、`interface.shortDescription`。
- 聚合该插件下的 skills 数量和统计。

Tools / Apps 解析规则：

- MVP 阶段从插件清单中提取可见的接口、能力说明和疑似工具入口。
- 如果没有稳定本地结构，仍显示“来源于插件清单/当前未发现运行时详情”的状态，不阻塞核心 Skills 功能。

## 使用统计

统计器只读 `sessions/**/*.jsonl`，以 skill 为主：

- `usageCount`：真实使用次数，来自用户显式 `$skill` 调用和助手读取对应 `SKILL.md` 的记录。
- `sessionsUsed` / `mentions`：兼容旧缓存和调试，不作为 UI 主指标。
- `lastUsedAt`：最近出现该 skill 的会话文件时间。

统计读取会做大小保护：逐文件流式扫描，不一次性把所有历史加载进内存。隐藏项仍保留统计。

## AI 离线整理

AI 整理由用户手动触发。实现方式：

1. 生成一个临时输入 JSON，写入项目内 `.tmp/ai-input.json`。
2. 调用本机 `codex` 命令行，让其根据原始数据生成结构化整理结果。
3. 输出写入项目内 `.tmp/ai-output.json`。
4. 解析成功后只合并到 AI 数据层。
5. 调用失败、超时或输出格式错误时，在 UI 显示错误，不影响本地扫描和个人数据。

为了避免长上下文，AI 整理默认按当前筛选列表或分批处理，不一次性塞入全部历史会话。

## 功能阶段

### 阶段 1：MVP Skills 字典

- Go 项目和数据模型。
- Skill 扫描、列表、搜索、详情。
- 收藏、隐藏、备注、用户标签。
- 打开 `SKILL.md`、打开目录、复制路径、复制调用模板。
- 基础单元测试和一次手动运行验证。

### 阶段 2：Plugins / Tools / Apps 辅助视图

- Plugin 清单扫描和详情。
- Tools / Apps 辅助视图从插件清单提取可解释信息。
- 视图切换、排序和状态标注。

### 阶段 3：使用统计

- 解析 Codex 历史会话。
- 展示真实使用次数和最近使用时间。
- Plugin 统计按下属 skills 聚合。

### 阶段 4：AI 离线整理和手动刷新

- AI 整理命令封装。
- AI 字段合并。
- 刷新能力清单、刷新统计、AI 整理当前列表、全部刷新。

### 阶段 5：侧边栏体验、快捷键、打包

- 置顶、靠右侧定位。
- 全局快捷键显示/隐藏。
- 构建 Windows GUI 可执行文件。
- 中文 README/使用说明。
- 完成测试、审查和修复。

## 测试与审查策略

每个小功能按以下流程推进：

1. 收集背景信息：读取本地结构、相关代码和样例数据。
2. 写小方案：在实施计划和开发记录里注明本次改动。
3. 开发：尽量先写测试，再写实现。
4. 验证：运行 Go 单元测试、构建命令和必要的手动 smoke test。
5. 审查：用独立审查步骤或子 agent 检查代码是否满足约束。
6. 修复：审查或测试发现问题后先修复，再进入下一个功能。

## 完成标准

- 当前项目内有可读源码和中文说明。
- Windows 可执行文件或便携包位于 `dist/`。
- 扫描、搜索、详情、模板复制、文件打开、收藏、隐藏、备注、刷新、统计、AI 整理入口、快捷键都经过验证。
- 测试通过，审查问题已处理。
- 没有任何构建命令需要写入当前项目外目录。
